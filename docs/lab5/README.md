# Практична робота №5 · Error-handling bottlenecks

## Запуск W Store

З кореня проєкту виконайте в PowerShell:

```powershell
cd backend
npm.cmd ci
npm.cmd start
```

`npm.cmd ci` встановлює залежності й потрібна перед першим запуском або після зміни залежностей. Роботу перевірено з Node.js 24.16.0. Express обслуговує каталог і API на порту 3000. Відкрийте [каталог W Store](http://localhost:3000/catalog) і натисніть **Load items**.

- [Корінь API](http://localhost:3000/) показує текст «API W Store працює».
- [Healthcheck](http://localhost:3000/health) повертає `200` і `{"status":"ok"}`.
- [Список товарів](http://localhost:3000/items) повертає JSON із SQLite.

Дані зберігаються у `backend/database.sqlite`. Під час запуску сервер за потреби додає поля й таблицю ключів ідемпотентності зі збереженням наявних товарів.

## Реалізовані вимоги

| Вимога | Поведінка |
| --- | --- |
| Ідемпотентний `POST /items` | Заголовок `Idempotency-Key` обов’язковий. SQLite атомарно створює товар і зберігає результат для цього ключа. Паралельні та наступні запити з тим самим ключем і даними повертають той самий ID і `201`, зокрема після перезапуску. Якщо дані відрізняються, API повертає `409`. |
| `X-Request-Id` | Express додає заголовок до успішних і помилкових відповідей, зокрема до CORS preflight. Клієнт створює окремий ID для кожної спроби, сервер повертає отриманий ID або генерує свій за відсутності заголовка. |
| Єдиний формат помилок | JSON містить `error`, `code`, `details` і `requestId`. Значення `requestId` збігається з `X-Request-Id` у відповіді. |
| Ліміт запитів | До 8 запитів з однієї IP-адреси до `/items` за 10 секунд в одному процесі сервера. Після цього API повертає `429`, а `Retry-After` містить округлений угору залишок вікна в секундах. |
| Автоматичні повтори | Для `429`, усіх `5xx`, мережевих помилок і таймаутів клієнт робить до двох повторів для `GET`, `HEAD` і `POST` з ключем ідемпотентності. Базова затримка зростає з 250 до 500 мс, jitter додає від 0 до 99 мс. |
| `Retry-After` | Підтримуються секунди та HTTP-дати. Клієнт використовує більшу із затримок сервера й backoff, потім додає jitter. За відсутнього, некоректного або минулого значення використовується backoff із jitter. |
| Таймаут | `AbortController` обмежує кожну спробу до 1000 мс, включно з читанням тіла відповіді. |
| Degraded Mode | Три поспіль операції, які вичерпали повтори через тимчасові збої, вмикають банер і блокують усі кнопки каталогу на 5 секунд. Успішна операція скидає лічильник. |
| `GET /health` | Повертає `{"status":"ok"}` незалежно від ліміту та демонстраційних збоїв на `/items`. |

CRUD використовує існуючі маршрути `GET /items`, `GET /items/:id`, `POST /items`, `PUT /items/:id` і `DELETE /items/:id`.

## Демонстрація в браузері

Для контрольованих збоїв зупиніть поточний сервер через **Ctrl+C** і запустіть із каталогу `backend`:

```powershell
$env:W_STORE_DEMO_FAULTS = '1'
npm.cmd start
```

Відкрийте DevTools → **Network**. У каталозі під списком товарів відображається журнал спроб і затримок.

1. **Паралельний POST.** У [звичайному каталозі](http://localhost:3000/catalog) задайте назву тестового товару та натисніть **Подвійний клік (Ідемпотентність)**. Перевірте два `POST /items` з однаковим `Idempotency-Key` і різними `X-Request-Id`. Обидва повернуть `201` з тим самим ID. **Load items** покаже один новий товар.
2. **429 і Retry-After.** Відкрийте [каталог із fault=429](http://localhost:3000/catalog?fault=429) й натисніть **Load items**. У відповіді буде `Retry-After: 1`, а в журналі — затримка щонайменше 1000 мс перед кожним повтором.
3. **Успішний повтор після реального ліміту.** Відкрийте звичайний каталог і дайте попередньому вікну ліміту 10 секунд завершитися. У **Console** виконайте рядок нижче. Перші вісім запитів займуть доступні місця у вікні. Натискання **Load items** у тому самому рядку запустить запит, що отримає `429`, дочекається `Retry-After` і отримає `200`.

   ```javascript
   await Promise.all(Array.from({ length: 8 }, () => fetch('/items', { cache: 'no-store' }))); document.querySelector('#loadBtn').click();
   ```

4. **5xx і таймаут.** На сторінках [fault=500](http://localhost:3000/catalog?fault=500), [fault=502](http://localhost:3000/catalog?fault=502), [fault=503](http://localhost:3000/catalog?fault=503) і [fault=504](http://localhost:3000/catalog?fault=504) натисніть **Load items** і перевірте початкову спробу та два повтори. На сторінці [fault=timeout](http://localhost:3000/catalog?fault=timeout) сервер затримує відповіді на 1300 мс, а браузер скасовує кожну спробу приблизно через 1000 мс. Для мережевого збою завантажте звичайний каталог, виберіть **Offline** у DevTools і натисніть **Load items**.
5. **Degraded Mode.** На сторінці [fault=503](http://localhost:3000/catalog?fault=503) тричі натисніть **Load items**, щоразу дочекавшись завершення двох повторів. Після третьої операції з’явиться банер, усі кнопки стануть неактивними, а через 5 секунд знову працюватимуть. Під час демонстрації [healthcheck](http://localhost:3000/health) продовжує повертати `{"status":"ok"}`.

Щоб повернутися до звичайного запуску, зупиніть сервер, виконайте `Remove-Item Env:W_STORE_DEMO_FAULTS` у тому самому PowerShell і знову запустіть `npm.cmd start`.

## Автоматизовані тести

З каталогу `backend` виконайте:

```powershell
npm.cmd test
```

Тести охоплюють CRUD, міграцію старої схеми, паралельні запити через два з’єднання SQLite, повтор після перезапуску, відкат запису, втрату відповіді після успішного запису, формат помилок, кореляцію, rate limiting і відновлення після `429`, `Retry-After`, тимчасові збої, таймаут і стан кнопок та банера каталогу. Для інтеграційних тестів використовуються тимчасові файли або SQLite в пам’яті.
